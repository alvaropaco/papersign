### CI/image workflow

Replace the upstream `publish.yml` and tag-based `deploy.yml` with a Papersign deploy workflow:

- Trigger: push to `main` plus manual dispatch.
- Runner: `ubuntu-latest`; single `linux/amd64` image because the VPS is amd64.
- Registry: GHCR using the built-in `GITHUB_TOKEN`.
- Image: `ghcr.io/alvaropaco/papersign`.
- Tags: full commit SHA, `sha-<short7>`, and `latest` as a convenience tag only.
- After image publish, a GitOps bump job will:
  - clone `alvaropaco/k8s-infra` branch `master` using repository secret `K8S_INFRA_PAT`;
  - update `tag:` in `apps/papersign/values.yaml` to the full commit SHA;
  - commit as `civ-bot <ci@0xcloud.net>` with `[skip ci]`;
  - push to `master`.
- The bump job will exit safely with a warning if the PAT or chart file is not yet present, avoiding a failed one-time bootstrap.

Required repository secret: `K8S_INFRA_PAT`, a fine-grained PAT with Contents write to `alvaropaco/k8s-infra`. GitHub Actions must also be enabled for the fork.

## 3. Required manual prerequisites

Before Papersign can become healthy:

1. Create/populate the Infisical project path `/papersign` with:
   - `NEXTAUTH_SECRET`
   - `NEXT_PRIVATE_ENCRYPTION_KEY`
   - `NEXT_PRIVATE_ENCRYPTION_SECONDARY_KEY`
   - `POSTGRES_PASSWORD`
   - `NEXT_PRIVATE_DATABASE_URL`
   - `NEXT_PRIVATE_DIRECT_DATABASE_URL`
   - `NEXT_PRIVATE_SMTP_PASSWORD`
   - `NEXT_PRIVATE_SIGNING_PASSPHRASE`
   - `SIGNING_CERT_P12_BASE64`
2. Grant the cluster’s Infisical machine identity access to that project.
3. Create the `papersign` namespace.
4. Copy `infisical-universal-auth-credentials` into that namespace.
5. Create or copy the `ghcr-pull` registry secret into that namespace.
6. Create the Cloudflare record for `app.papersign.io`.
7. Create the Mailcow mailbox and DNS authentication records for `noreply@papersign.io`.
8. Set `K8S_INFRA_PAT` on the Papersign repository and enable GitHub Actions.

The signing certificate is optional for first boot: `/api/health` will warn but still serve if it is absent.

## 4. Deployment sequence

1. Commit the completed Papersign rebrand.
2. Commit Papersign deployment/CI changes.
3. Push `main` and wait for the Docker publish workflow to finish.
4. Pull the latest k8s-infra `master`.
5. Add the Papersign chart with the published commit SHA pinned as the initial tag.
6. Run `helm lint apps/papersign` and `helm template papersign apps/papersign --namespace papersign`.
7. Commit and push k8s-infra `master`.
8. Wait for ArgoCD to sync the new Application.
9. Verify:
   - ArgoCD Application is Synced and Healthy;
   - Papersign pod passes `/api/health`;
   - Postgres StatefulSet is healthy;
   - `https://app.papersign.io` loads and serves Papersign;
   - `app.papersign.io.157.173.121.7.nip.io` works as the DNS fallback;
   - future Papersign pushes bump the k8s-infra tag successfully.
10. After verification, remove `argocd/apps/documenso.yaml` and `apps/documenso/` in a separate commit so ArgoCD prunes the old app. Leave the old Postgres PVC/data in place as a recovery snapshot.

## 5. Validation and rollback

- Papersign validation: targeted typechecks, library unit tests, workflow YAML review, Docker build/publish through CI, and Helm lint/template.
- k8s-infra validation: the repository’s existing Helm lint workflow plus local Helm template inspection.
- Post-deploy checks: ArgoCD health, pod logs, `/api/health`, public URL, legacy redirect, SMTP configuration, and Prisma migration logs.
- Rollback strategy: revert the k8s-infra tag bump to the previous full SHA; ArgoCD will roll the Deployment back. For chart-level failures, revert the k8s-infra commit.
